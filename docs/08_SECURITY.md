# Security & 152-ФЗ — ЗаказАвто

## Назначение документа

Описание мер безопасности, защиты персональных данных и соответствия требованиям 152-ФЗ.

---

## 1. Общие принципы

1. **Минимизация данных** — собирать только необходимые ПДн
2. **Защита передачи** — HTTPS везде, шифрование транспорта
3. **Защита хранения** — хеширование паролей, шифрование чувствительных данных
4. **Ограничение доступа** — RBAC, логирование доступа к ПДн
5. **Обезличивание** — где возможно, использовать обезличенные идентификаторы
6. **Согласие** — получать явное согласие на обработку ПДн
7. **Прозрачность** — клиент должен знать, какие данные собираются и зачем

---

## 2. Персональные данные (152-ФЗ)

### 2.1 Какие ПДн собираются

**Клиенты:**
- Имя
- Телефон
- Email (опционально)
- Telegram username (опционально)
- Адрес доставки (опционально, при оформлении заказа)

**Сотрудники:**
- Email
- Имя
- Пароль (хешированный)

### 2.2 Согласие на обработку ПДн

**Обязательно** при первой отправке заявки:

```
☑ Я согласен на обработку персональных данных в соответствии 
  с Политикой конфиденциальности
```

**Форма согласия должна быть:**
- Явной (checkbox, а не pre-checked)
- Добровольной (нельзя отправить заявку без согласия)
- С ссылкой на Политику конфиденциальности

**Хранение согласия:**
- Дата и время согласия
- IP-адрес (для подтверждения)
- Версия политики

### 2.3 Политика конфиденциальности

**Обязательно** опубликовать на сайте.

**Содержание:**
- Какие данные собираются
- Для каких целей
- Как долго хранятся
- Кому передаются (если передаются)
- Как защищаются
- Права субъекта ПДн
- Контакты для обращений

### 2.4 Защита ПДн

**Хранение в БД:**
- Пароли: bcrypt (cost factor ≥ 10)
- Чувствительные данные: шифрование на уровне приложения (опционально, если требуется)

**Передача:**
- HTTPS везде (TLS 1.2+)
- Не передавать ПДн в URL (query parameters)
- Не передавать ПДн в Telegram и другие внешние системы

**Доступ:**
- Только авторизованные сотрудники
- Логирование доступа к ПДн
- Регулярный аудит логов

### 2.5 Telegram-уведомления (критически важно)

**Нельзя передавать:**
- Имя клиента
- Телефон
- Email
- Telegram username
- Адрес
- Любые другие ПДн

**Можно передавать:**
- ID заявки (например, "Новая заявка #1234")
- ID автомобиля
- Статус заказа
- Обезличенную техническую информацию

**Пример безопасного уведомления:**

```
✅ Новая заявка #1234

Тип: Подбор автомобиля
Марка: Toyota
Бюджет: 3 000 000 ₽

🔗 Открыть в админке: https://admin.zakazavto.ru/orders/1234
```

### 2.6 Права субъекта ПДн

Клиент имеет право:
- Получить копию своих ПДн
- Исправить неточные ПДн
- Удалить свои ПДн (право на забвение)
- Отозвать согласие на обработку

**Реализация:**
- Форма обращения на сайте или email
- Ответ в течение 30 дней
- Удаление ПДн (кроме случаев, когда хранение обязательно по закону)

### 2.7 Обезличивание

**В публичных кейсах и отзывах:**
- Не публиковать полное имя без согласия
- Использовать обезличенные варианты: "Иван К.", "Клиент из Москвы"
- Не публиковать телефон, email, адрес

**В аналитике:**
- Не хранить ПДн в системах аналитики
- Использовать анонимные идентификаторы

## 3. Аутентификация и авторизация

### 3.1 Админ-панель

**Аутентификация:**
- JWT токены
- Access token (short-lived, 1 час)
- Refresh token (long-lived, 7 дней)

**Пароли:**
- Минимум 8 символов
- Обязательно: буквы + цифры
- Хеширование: bcrypt (cost 10)

**Защита от брутфорса:**
- Rate limiting: максимум 5 попыток входа в 15 минут
- Temporary lock после 5 неудачных попыток (15 минут)
- Логирование всех попыток входа

**Выход из системы:**
- Инвалидация токена
- Очистка cookies/localStorage

### 3.2 RBAC (будущая функция)

**Роли (на старте все с одинаковыми правами):**
- Admin — полный доступ
- Manager — работа с заказами и клиентами
- Supervisor — только просмотр отчётов

**Архитектура должна поддерживать RBAC для будущего расширения.**

## 4. Публичный сайт

### 4.1 Защита форм

**CSRF Protection:**
- CSRF-токены для всех POST-форм
- Проверка токена на backend

**Валидация:**
- Серверная валидация (не полагаться только на клиентскую)
- Zod-схемы для валидации входных данных

**Санитизация:**
- Экранирование HTML (React делает автоматически)
- Валидация email, телефона, URL

**Rate Limiting:**
- Заявки: максимум 5 в минуту с одного IP
- Отслеживание заказа: максимум 10 запросов в минуту с одного IP

### 4.2 Защита от ботов

**reCAPTCHA v3** (опционально, если будет спам)

**Honeypot поля** (скрытые поля для ботов)

### 4.3 XSS Protection

**React** автоматически экранирует вывод.

**Дополнительно:**
- `Content-Security-Policy` заголовок
- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: DENY`

### 4.4 SQL Injection Protection

**Prisma** автоматически защищает (параметризованные запросы).

**Не использовать** raw SQL без параметров.

## 5. API

### 5.1 Rate Limiting

```
Публичные эндпоинты:  100 requests/minute/IP
Заявки (POST /leads): 5 requests/minute/IP
Отслеживание заказа:  10 requests/minute/IP
Админ-панель:         1000 requests/minute/user
```

### 5.2 CORS

**Настройка:**
```javascript
{
  origin: ['https://zakazavto.ru', 'https://admin.zakazavto.ru'],
  methods: ['GET', 'POST', 'PATCH', 'DELETE'],
  credentials: true
}
```

### 5.3 Валидация входных данных

**Все эндпоинты** должны валидировать входные данные через Zod-схемы.

**Примеры:**
- `vehicleId` — должен быть UUID
- `email` — должен быть валидным email
- `phone` — должен соответствовать формату

### 5.4 Безопасные идентификаторы

**UUID v4** для всех ID (вместо auto-increment).

**Обоснование:**
- Нельзя перебрать
- Нельзя предсказать следующий ID
- Безопасность через сложность

## 6. Отслеживание заказа

### 6.1 Защита tracking token

**Генерация:**
- UUID v4 (128-bit энтропия)
- Уникальный для каждого заказа

**Передача:**
- Только через уникальную ссылку (не публичный поиск)
- HTTPS обязательно

**Защита от перебора:**
- Rate limiting (10 requests/minute/IP)
- Сложность токена (UUID v4) делает перебор невозможным

**Публичные данные:**
- Только то, что помечено `isPublic: true` в timeline
- Не показывать ПДн клиента (имя, телефон, email)
- Не показывать внутренние заметки менеджера

### 6.2 Защита от утечки токенов

**Не передавать токен через:**
- Email (если email скомпрометирован)
- SMS (если телефон потерян)

**Передавать только:**
- Лично клиенту при оформлении заказа
- Через защищённый личный кабинет (будущая функция)

## 7. Файловое хранилище

### 7.1 Загрузка файлов

**Ограничения:**
- Максимальный размер: 10 MB (фото), 100 MB (видео), 20 MB (документы)
- Разрешённые типы: JPEG, PNG, WebP, MP4, WebM, PDF, DOC, DOCX

**Валидация:**
- Проверка MIME-типа
- Проверка расширения файла
- Проверка magic bytes (первые байты файла)

**Санитизация имён файлов:**
- Убирать небезопасные символы
- Использовать UUID для имён файлов

### 7.2 Публичный доступ

**Фото и видео автомобилей:** публичные (через CDN)

**Документы клиентов:** защищённые (требуют авторизации)

**Отчёты о проверке:** решение не зафиксировано (можно сделать публичными с уникальной ссылкой)

## 8. Логирование

### 8.1 Что логировать

**Обязательно:**
- Ошибки (500, 404)
- Попытки входа (успешные и неудачные)
- Доступ к ПДн (кто, когда, какие данные)
- Изменения критических данных (заказы, клиенты, финансы)
- API запросы (метод, URL, IP, user-agent, status code, response time)

**Опционально:**
- Debug-информация (только development)

### 8.2 Формат логов

```javascript
{
  timestamp: "2026-08-22T14:30:00Z",
  level: "info" | "warn" | "error",
  message: "User login successful",
  userId: "uuid",
  ip: "192.168.1.1",
  userAgent: "Mozilla/5.0...",
  context: { ... }
}
```

### 8.3 Хранение логов

**Development:** консоль

**Production:**
- Файлы (ротация ежедневно, хранение 30 дней)
- Sentry (ошибки)

**Не логировать:**
- Пароли
- Токены
- Полные данные кредитных карт (если будет онлайн-оплата)

## 9. Резервное копирование

### 9.1 База данных

**Частота:** ежедневно (ночью)

**Хранение:** минимум 7 дней, рекомендуется 30 дней

**Тестирование восстановления:** 1 раз в месяц

### 9.2 Файловое хранилище

**Частота:** еженедельно (если не используется S3 с версионированием)

**Хранение:** минимум 30 дней

### 9.3 Код

**Git** — репозиторий на GitHub/GitLab с приватным доступом

**Резервные копии репозитория:** автоматически (GitHub/GitLab)

## 10. Инциденты безопасности

### 10.1 План реагирования

**При обнаружении утечки ПДн:**

1. Немедленно заблокировать доступ к скомпрометированным данным
2. Оценить масштаб утечки
3. Уведомить Роскомнадзор (в течение 24 часов, если утечка > 1000 субъектов)
4. Уведомить затронутых клиентов
5. Провести расследование
6. Устранить уязвимость
7. Обновить процедуры безопасности

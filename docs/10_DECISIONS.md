# Architectural Decisions — ЗаказАвто

## Назначение документа

Фиксация принятых архитектурных и продуктовых решений с обоснованием.

---

## 1. Архитектурные решения

### АР-001: Модульный монолит вместо микросервисов

**Решение:** Использовать модульный монолит.

**Обоснование:**
- MVP не требует распределённой архитектуры
- Проще разработка, деплой и отладка
- Ниже операционные расходы
- Возможность разделения на микросервисы в будущем (если модули правильно изолированы)

**Альтернативы:** Микросервисы (отклонены как overengineering для MVP).

---

### АР-002: Next.js как единый фреймворк

**Решение:** Использовать Next.js 14+ для frontend и backend (API Routes).

**Обоснование:**
- SSR/SSG для SEO
- Единый проект упрощает деплой
- TypeScript end-to-end
- Встроенная оптимизация (images, fonts)
- Большое комьюнити

**Альтернативы:** Разделение на отдельный backend (Node.js + Express) и frontend (Next.js) — отклонено для упрощения MVP.

---

### АР-003: PostgreSQL как основная БД

**Решение:** PostgreSQL на Supabase.

**Обоснование:**
- Надёжность и стабильность
- Поддержка JSON
- Полнотекстовый поиск
- Бесплатный хостинг (Supabase free tier)
- Автоматические бэкапы

**Альтернативы:** MySQL (меньше функций), MongoDB (нет строгой схемы) — отклонены.

---

### АР-004: Prisma как ORM

**Решение:** Prisma.

**Обоснование:**
- TypeScript-first
- Автоматическая генерация типов
- Миграции
- Prisma Studio для разработки
- Защита от SQL-инъекций

**Альтернативы:** TypeORM (более сложный), Drizzle (менее зрелый) — отклонены.

---

### АР-005: UUID вместо auto-increment ID

**Решение:** Использовать UUID v4 для всех идентификаторов.

**Обоснование:**
- Безопасность (нельзя перебрать)
- Невозможность предсказать следующий ID
- Подходит для распределённых систем (будущее)

**Альтернативы:** Auto-increment (предсказуемые ID, менее безопасно) — отклонено.

---

### АР-006: Централизованный финансовый движок

**Решение:** Единый модуль расчёта цен.

**Обоснование:**
- Консистентность расчётов
- Лёгкое изменение формулы
- Централизованное тестирование
- Не размазывать логику по UI-компонентам

**Альтернативы:** Дублировать расчёты в разных местах — отклонено (DRY violation, риск ошибок).

---

### АР-007: Ручной каталог (не автоимпорт)

**Решение:** Автомобили добавляются только вручную через админ-панель.

**Обоснование:**
- Контроль качества данных
- Кураторский подход (не агрегатор)
- Меньше сложности в MVP
- Соответствует бизнес-модели (15-25 авто/месяц)

**Альтернативы:** Автоматический импорт с аукционов — отклонён для MVP (можно добавить позже).

---

### АР-008: Обезличивание Telegram-уведомлений

**Решение:** Telegram-уведомления не содержат ПДн клиентов.

**Обоснование:**
- Соответствие 152-ФЗ
- Минимизация рисков утечки
- Принцип минимизации данных

**Пример безопасного уведомления:**
```
✅ Новая заявка #1234
Тип: Подбор автомобиля
Марка: Toyota
Бюджет: 3 000 000 ₽
🔗 Открыть в админке
```

**Альтернативы:** Передавать ПДн в Telegram — отклонено (нарушение 152-ФЗ).

---

### АР-009: Tracking token вместо публичного поиска

**Решение:** Отслеживание заказа через уникальный токен (UUID v4) в URL.

**Обоснование:**
- Безопасность (нельзя перебрать заказы)
- Защита ПДн (нельзя найти заказ по публичному номеру)
- Простота реализации

**Пример:** `https://zakazavto.ru/track/a1b2c3d4-e5f6-7890-abcd-ef1234567890`

**Альтернативы:** Публичный поиск по номеру заказа — отклонено (риск утечки ПДн).

---

### АР-010: Mobile-first подход

**Решение:** Проектировать и разрабатывать сначала для мобильных устройств.

**Обоснование:**
- Основной пользователь на мобильном
- Лучше UX на всех устройствах
- Приоритизация контента

**Минимальные тестовые размеры:** 360px, 390px, 430px, desktop.

---

### АР-011: Cloudflare R2 для файлов

**Решение:** Cloudflare R2 для хранения фото/видео/документов.

**Обоснование:**
- Бесплатный egress (в отличие от AWS S3)
- S3-совместимый API
- Интеграция с Cloudflare CDN
- Низкая стоимость

**Альтернативы:** AWS S3 (дороже egress), DigitalOcean Spaces (меньше регионов) — приемлемые альтернативы.

---

### АР-012: Vercel для хостинга

**Решение:** Vercel для деплоя Next.js приложения.

**Обоснование:**
- Нативная поддержка Next.js
- Автоматический деплой из Git
- Глобальный CDN
- Serverless Functions
- Бесплатный план для стартапов
- Preview deployments

**Альтернативы:** VPS (требует настройки, больше обслуживания) — приемлемая альтернатива для большего контроля.

---

### АР-013: JWT для аутентификации админ-панели

**Решение:** JWT-токены (Access + Refresh) для админ-панели.

**Обоснование:**
- Простота реализации
- Stateless (не требуется session store)
- Подходит для Next.js API Routes

**Security:**
- Access token: 1 час
- Refresh token: 7 дней
- httpOnly cookies (если используются)

**Альтернативы:** NextAuth.js — overengineering для только админ-панели.

---

### АР-014: Tailwind CSS для стилизации

**Решение:** Tailwind CSS + Radix UI.

**Обоснование:**
- Utility-first подход
- Быстрая разработка
- Хорошая производительность (PurgeCSS)
- Встроенная респонсивность
- Radix UI для accessibility

**Альтернативы:** CSS-in-JS (styled-components, Emotion) — медленнее, CSS Modules — больше бойлерплейта.

---

### АР-015: Разделение публичных и внутренних данных

**Решение:** Публичные API возвращают только разрешённые данные.

**Обоснование:**
- Безопасность ПДн
- Гибкость показа/скрытия финансовой информации
- Разделение timeline на публичные и внутренние события

**Реализация:** Поле `isPublic` в timeline, `showPricePublic` в vehicles.

---

### АР-016: Единый репозиторий (monorepo не требуется)

**Решение:** Единый Git-репозиторий для frontend и backend.

**Обоснование:**
- Next.js объединяет frontend и backend
- Проще синхронизация типов (TypeScript)
- Меньше сложности в CI/CD

**Альтернативы:** Monorepo (Turborepo, Nx) — overengineering для MVP.

## 2. Продуктовые решения

### ПР-001: Не делать каталог центром продукта

**Решение:** Каталог — второстепенная функция, основа — сервис и доверие.

**Обоснование:**
- Дифференциация от конкурентов (агрегаторов)
- Соответствие бизнес-модели (ручной подбор)
- Фокус на доказательствах опыта, а не на количестве лотов

---

### ПР-002: Проверка автомобиля — центральный элемент

**Решение:** Сделать проверку главным trust-элементом сайта.

**Обоснование:**
- Дифференциация от конкурентов
- Соответствует ценности компании
- Формирует доверие

---

### ПР-003: Виталий как эксперт, бренд — главный

**Решение:** Показать Виталия как лицо и эксперта, но бренд ЗаказАвто остаётся главным.

**Обоснование:**
- Не превращать сайт в сайт частного перекупа
- Масштабируемость бренда (не зависимость от одного человека)
- Баланс персонализации и корпоративности

---

### ПР-004: Доверие ДО заявки, а не после

**Решение:** Сначала показать доказательства, затем просить заявку.

**Обоснование:**
- Психология пользователя (требовать веры до информации — плохой UX)
- Конкурентное преимущество
- Выше конверсия

---

### ПР-005: Публичный калькулятор не обязателен в MVP

**Решение:** Не делать публичный калькулятор в MVP.

**Обоснование:**
- Не зафиксировано окончательное решение о публичности цен
- Можно добавить позже (финансовый движок поддерживает)
- Упрощение MVP

---

### ПР-006: Отслеживание заказа — обязательная функция

**Решение:** Публичное отслеживание заказа входит в MVP.

**Обоснование:**
- Ключевая ценность компании (контроль на всех этапах)
- Дифференциация от конкурентов
- Прозрачность процесса

---

### ПР-007: Кейсы важнее стандартных отзывов

**Решение:** Реальные кейсы (от задачи до результата) вместо карусели цитат.

**Обоснование:**
- Более убедительное доказательство
- Показывает реальный процесс работы
- Дифференциация от конкурентов

---

## 3. Дизайн-решения

### ДР-001: Чёрный/красный/белый как основа

**Решение:** Primary: Red 600 (#DC2626), Neutral: Black/White/Gray.

**Обоснование:**
- Соответствует предпочтениям клиента
- Автомобильная эстетика
- Не визуально дешёвая кислотная красная

---

### ДР-002: Не копировать automotive-стандарт

**Решение:** Создать самостоятельный визуальный язык.

**Обоснование:**
- Дифференциация
- Современный digital-сервис, а не просто автосалон
- Отражение технологичности и прозрачности

---

### ДР-003: Системный шрифт вместо веб-шрифта

**Решение:** Использовать системный font-stack (или Inter как альтернатива).

**Обоснование:**
- Производительность (нет загрузки шрифта)
- Нативное ощущение для пользователя
- Хорошая читаемость на всех устройствах

## 4. Технические решения

### ТР-001: Rate limiting для защиты

**Решение:** Настроить rate limiting для всех публичных эндпоинтов.

**Обоснование:**
- Защита от спама (заявки)
- Защита от DDoS
- Защита от перебора (tracking)

**Лимиты:** 100/min (общий), 5/min (заявки), 10/min (tracking).

---

### ТР-002: HTTPS обязательно везде

**Решение:** Все соединения только через HTTPS.

**Обоснование:**
- Защита ПДн
- Требование 152-ФЗ
- SEO (Google ранжирует HTTPS выше)

---

### ТР-003: Логирование доступа к ПДн

**Решение:** Логировать все обращения к ПДн клиентов.

**Обоснование:**
- Требование 152-ФЗ
- Возможность аудита при инцидентах
- Контроль несанкционированного доступа

---

### ТР-004: Резервное копирование ежедневно

**Решение:** Автоматические бэкапы БД ежедневно, хранение 7+ дней.

**Обоснование:**
- Защита от потери данных
- Возможность восстановления при сбое
- Обязательная практика production-систем

---

### ТР-005: Тестирование восстановления 1 раз в месяц

**Решение:** Проверять возможность восстановления из бэкапа.

**Обоснование:**
- Бэкапы без проверки восстановления бесполезны
- Подготовка к реальному инциденту

## 6. Правила для coding AI

### Правило-001: Не придумывать данные

Если данных компании нет — использовать placeholder:
```
CONTENT_REQUIRED
IMAGE_PLACEHOLDER: [описание]
```

Не использовать случайные стоковые фотографии.

---

### Правило-002: Не изменять финансовую формулу без подтверждения

Формула расчёта зафиксирована в DATA_MODEL.md.

Любое изменение требует явного одобрения.

---

### Правило-003: Не передавать ПДн в Telegram

Строго обезличивать уведомления.

Любое нарушение — критическая ошибка.

---

### Правило-004: Не копировать конкурентов

Анализ конкурентов — для понимания рынка, а не для копирования.

Создавать самостоятельные решения.

---

### Правило-005: Mobile-first всегда

Все компоненты сначала проектируются для мобильных, затем адаптируются для desktop.
